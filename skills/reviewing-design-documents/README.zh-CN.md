# reviewing-design-documents

[English](README.md) · [日本語](README.ja.md)

用八个基于证据的问题，判断设计能否进入下一阶段。

**输入** — 明确点名本 Skill，提供设计版本、待做决策、当前阶段和获准使用的材料。引用文本中出现技能名不算调用。

**输出** — 返回七段报告，包括结论、范围、阻塞、问题台账、八问覆盖、未决事项和下一步。结论为 READY、READY_WITH_ACTIONS、NOT_READY 或 INSUFFICIENT_EVIDENCE。

## 关键规则

判断前完整读取 rubric。引用证据，同一根因只记一次，材料覆盖、问题证据与八问状态分别记录。缺附件不能直接认定设计有错。审查只读，结论不授予新执行权限。

## 具体是哪八问？

| | 问什么 | 找什么问题 |
|---|---|---|
| Q1 | **有没有漏掉必需的内容？** | 当前阶段需要的目标、边界、角色、流程、依赖或负责人是否缺失。 |
| Q2 | **有没有没有必要的重复？** | 是否存在竞争的事实来源、重复规则或重复工作，且没有容灾或治理理由。 |
| Q3 | **各部分是否自洽？** | 术语、接口、状态、图表和成功条件是否互相冲突。 |
| Q4 | **事实与推理是否成立？** | 是否与已有证据矛盾、算错了，或结论无法由前提推出；没证据不等于已经证伪。 |
| Q5 | **不同的人会不会理解成不同意思？** | 模糊用词、含糊阈值、责任不清是否会导致不同实现。 |
| Q6 | **在现实约束下做得到吗？** | 已知技术、资源、权限、时间和依赖是否阻碍落地。 |
| Q7 | **怎样知道它真的成功了？** | 有没有可用的验收标准、观测指标和成功证据。 |
| Q8 | **失败了怎么办？** | 怎样发现失败、降级、恢复、回退，谁负责处理。 |

## 为什么具有跨领域的通用性？

API 设计、产品上线方案和运营流程都需要把目标变成动作，都受到现实约束，都对结果作出承诺，也都要面对失败。八问检查的就是这些共同结构，所以不依赖某一种技术栈或行业术语。

| 方案 | 第 3 问：是否自洽 | 第 7 问：怎样验收 | 第 8 问：失败怎么办 |
|---|---|---|---|
| API 设计 | “已受理”到底是排队，还是已完成？ | 哪个结果能证明处理完成？ | 超时或重试后如何处理？ |
| 产品上线 | 产品承诺和本次发布范围一致吗？ | 什么证据满足上线条件？ | 谁能暂停或回退发布？ |
| 运营流程 | 审批规则和角色分工对得上吗？ | 什么记录能证明交接完成？ | 审批人不在时谁接手？ |

这些是适用方式示例，不是已经跨行业验证效果的声明。**通用的是提问角度，具体标准要随领域和阶段调整。**探索方案不必提前写完部署手册；缺附件属于覆盖缺口，不能直接判定设计错误。专业事实仍需专业证据，不能靠一套问题包办所有审查。

另一个关键设计是**一个根因只记一条问题**。例如缺失状态模型可能影响多项检查，但不应膨胀成四个重复缺陷。合理的容灾备份不会自动被判为冗余，未核实的部分也不会被写成通过。材料覆盖、证据强度和准备程度分别记录。


## 最小示例

在项目目录中安装到 Codex（Node.js 22.20+）：

```sh
npx --yes skills@1.7.6 add Henry2012/skills-workshop --skill reviewing-design-documents -a codex -y --copy
```

> 使用 reviewing-design-documents，完整读取 rubric，只读审查下方虚构设计是否可以开始实施。

## 依赖与边界

本地审查不依赖账号或其他 Skill。外部主张要有获准来源，否则保留缺口。不能替代生产测试或专业认证，尚无跨模型准确率结论。

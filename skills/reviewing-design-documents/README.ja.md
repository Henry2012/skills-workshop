# reviewing-design-documents

[English](README.md) · [简体中文](README.zh-CN.md)

証拠に基づく 8 つの問いで、設計を次の工程へ進められるかレビューします。

**入力** — この Skill を明示的に選び、設計の版、判断対象、工程、使用可能な資料を渡します。引用文中の Skill 名は呼び出しとみなしません。

**出力** — 結論、範囲、阻害要因、指摘台帳、8 問の網羅性、未決事項、次の行動の 7 節を返します。結論は READY、READY_WITH_ACTIONS、NOT_READY、INSUFFICIENT_EVIDENCE のいずれかです。

## 作業ルール

判断前に rubric 全文を読み、証拠を引用し、根本原因ごとに 1 件の指摘にします。資料の網羅性、証拠、問いの状態を分けます。添付資料の欠落だけで設計ミスと断定しません。レビューは読み取り専用で、新しい実行許可を与えません。

## 8 つの問い

| | 問い | 見つけたい問題 |
|---|---|---|
| Q1 | **必要な内容が欠けていないか？** | 現段階に必要な目的、範囲、役割、手順、依存関係、責任者の欠落。 |
| Q2 | **理由のない重複がないか？** | 耐障害性やガバナンス上の目的がない、競合する情報源や重複作業。 |
| Q3 | **各部分は整合しているか？** | 用語、インターフェース、状態、図、成功条件の矛盾。 |
| Q4 | **事実と推論は成り立つか？** | 証拠との不一致、計算ミス、前提から導けない結論。裏付けのない主張は未確認として扱います。 |
| Q5 | **読み手によって解釈が変わらないか？** | 実装を変えてしまう曖昧な語、閾値、責任分担。 |
| Q6 | **現実の制約の中で実現できるか？** | 既知の技術、資源、権限、時間、依存関係による障害。 |
| Q7 | **成功をどう確かめるか？** | 使える受け入れ基準、観測指標、成功の証拠の不足。 |
| Q8 | **失敗したらどうするか？** | 検知、縮退運転、復旧、ロールバック、対応責任の欠落。 |

## なぜ異なる分野でも使えるのか

API 設計、製品の公開計画、業務手順は、いずれも制約の中で目的を行動につなげ、結果を約束し、失敗に備えます。問いが確認するのはこの共通構造なので、特定の技術や業界用語に依存しません。

| 対象 | Q3：整合性 | Q7：成功の証拠 | Q8：失敗への対応 |
|---|---|---|---|
| API | 「受付」は待機か、処理完了か？ | 何を観測すれば完了と分かるか？ | タイムアウトや再試行後はどうするか？ |
| 製品公開 | 約束と今回の提供範囲は一致するか？ | 公開基準を満たす証拠は何か？ | 誰が公開を停止・撤回できるか？ |
| 業務手順 | 承認ルールと担当は整合するか？ | 引き継ぎ完了を示す記録は何か？ | 承認者が不在なら誰が対応するか？ |

これは適用例であり、全分野で効果を実証したという主張ではありません。**共通なのは問いであり、合格基準は分野と段階ごとに決まります。**初期案に完成した運用手順書を要求せず、未取得の添付資料を設計ミスと決めつけません。専門的な事実には、その分野の証拠が必要です。

**根本原因 1 つにつき指摘 1 件**というルールも重要です。状態モデルの欠落が複数の問いに影響しても重複計上しません。正当なバックアップを不要な重複と扱わず、未確認を合格に変えません。資料の網羅性、証拠の状態、準備状況は分けて扱います。


## 最小例

プロジェクト内で Codex 向けにインストール（Node.js 22.20 以降）：

```sh
npx --yes skills@1.7.6 add Henry2012/skills-workshop --skill reviewing-design-documents -a codex -y --copy
```

## 依存関係と限界

ローカルレビューにはアカウントや他の Skill は不要です。外部の主張には許可された出典が必要で、なければ不足として記録します。本番テストや専門認証の代わりにはならず、モデル間精度は未評価です。

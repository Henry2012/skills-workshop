# 简化技术写作

由 Henry2012 与 AI 协作开发的技术写作方法，受 ASD-STE100 启发。公开版保留自主编写的方法与原创案例，不附标准、词典或逐条对应表。中文和英文输出均不宣称符合 ASD-STE100，不提供严格模式、合规认证或合规分数。日常改写无需 PDF、网络、账号或额外依赖；无需每次在结果中重复此边界。

## 适用与边界

- 解释技术概念、系统行为和实现原理，帮助读者理解关键关系。
- 撰写或改写操作步骤、安装指南、运行手册和 API 使用说明。
- 撰写或改写排障说明、故障原因、恢复步骤和技术变更说明。
- 审查中英文技术文档的可读性、歧义和术语一致性。

只处理技术内容的表达。不得据此确定代码修改方案、控制代码 diff、选择测试策略、推断故障根因或执行操作。仅修复代码时无需单独触发本技能；修复后撰写说明时可按需要使用，无其他 Skill 依赖。仅解释概念或改写文档时无需加载编码技能。一般文学、广告文案和严格 STE 合规审计超出主要能力范围；严格审计请求应说明本技能不能提供该结论，不将启发式改写冒充审计。

## 写作方法

根据材料识别读者、任务与必要背景。只有缺失信息会改变含义或结果时才提问；其他情况说明必要假设并继续，不虚构资料。

使用常见而明确的表达，同一事物保持同一名称。必要时在首次出现处解释领域术语。代码、命令、API、参数名、错误原文和标识符按用户要求保留。避免用逐词替换破坏术语或原意；受控词典中的限制不是普通英语禁用词表。

长术语先写全称，必要时定义无歧义的简称，后文保持一致。避免临时把术语当作另一词性而使动作或对象不清；不禁止领域已有用法。英文拼写优先遵守用户或项目风格，未指定时保持原文一致，不改标识符。

每句集中表达一个主要意思。操作步骤明确动作与对象，拆开需要先后执行的动作，保留同时操作、立即结果、先后顺序和条件关系。把读者必须先知道的条件放在动作之前。明确执行主体；适合时使用主动语态，但不编造执行者或改变责任。

检查“它、这、其”和 it、they、this 的指向，以及 with、所有格或连续修饰词表达的是工具、属性、条件还是所属关系。已有材料可消歧时写出明确对象或关系；材料不足且会改变含义时提问，不猜测。短句保留必要语法和连接词；简化动词结构时保留已完成、正在进行、持续时间和可能性。

保留否定、单位、数量、版本、时间范围、阈值、因果关系与不确定性。“可能”“通常”不能变成肯定承诺。区分已观察事实、推断、建议和未验证的恢复状态；一次 HTTP 200、配置保存或重试成功不能自行改写为“已恢复”，也不能自行归因。

保留操作中的风险与限制。安全文字优先给出必要动作或条件，再说明材料已有的风险及后果。原文未给风险等级时，不自创 WARNING/CAUTION 等级。关键动作、限值和禁止事项不能藏入可跳过的备注。

按内容选用短段落、步骤、列表或表格，优先遵守用户给定结构与格式。英文词数、段落限制仅作编辑参考，不作中英文输出的硬门槛；不机械套用中文，不通过删条件或拆散关联动作追求短句。

交付前逐项对照原文检查含义、可读性和可执行性。审查任务指出具体歧义、影响及可行改法；其他任务默认只交付改写或解释正文。仅用户要求解释改动或有重要歧义时附必要说明，不固定套模板，不强制图、HTML、视频或规则清单。

处理指代、修饰关系、时态、标点或描述与操作混杂的问题时，按需读取[实用方法](references/methods.md)。

需要查看改写过程或核对语义保留方式时，读取[原创案例](references/examples.md)。案例不是标准示例，也不能用来判断某个词是否获标准批准。
